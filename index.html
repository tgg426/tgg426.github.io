WebSocket vs SSE：流式数据传输的技术选型

引言

在实时应用开发中，选择合适的通信协议至关重要。WebSocket 和 SSE（Server-Sent Events）是两种常用的流式数据传输技术，各自有不同的应用场景和优势。本文将深入分析这两种技术，并根据不同业务场景提供选型建议。

核心技术对比

SSE (Server-Sent Events)

核心特征：

  • 📡 单向通信：服务端 → 客户端
  • 🔗 基于 HTTP 长连接
  • 🔄 自动重连机制
  • 📝 仅支持文本数据
  • 🚀 实现简单

工作机制：

WebSocket

核心特征：

  • 📱 双向通信：服务端 ⇄ 客户端
  • 🔌 独立协议（ws://, wss://）
  • ⚙️ 需手动实现重连
  • 📦 支持文本和二进制数据
  • 🎯 低延迟、高性能

工作机制：

功能特性对比表

特性 SSE WebSocket 说明
通信方向 单向（服务端→客户端） 双向（全双工） SSE 适合推送场景
协议基础 HTTP/1.1 独立协议 SSE 更轻量
数据格式 仅文本（UTF-8） 文本 + 二进制 WebSocket 功能更全
自动重连 ✅ 浏览器原生支持 ❌ 需手动实现 SSE 更省事
实现复杂度 ⭐ 简单 ⭐⭐ 中等 SSE 开发更快
浏览器兼容 现代浏览器 兼容性极好 WebSocket 历史更久
服务器开销 较低 较高（需心跳维持） SSE 资源占用少
代理友好 ✅ 完全兼容 HTTP 代理 ⚠️ 需要特殊配置 SSE 部署更简单

技术选型分析

场景一：AI 对话流式输出 ✅ SSE

典型应用： ChatGPT、Claude 等 AI 对话应用

为什么选择 SSE：

  • 单向数据流：AI → 用户
  • 自动重连确保用户体验
  • HTTP 协议穿透性强
  • 实现简单，维护成本低

性能对比

SSE 性能特点

  • 连接数： 可支持数万并发连接
  • 延迟： 略高于 WebSocket（HTTP 开销）
  • 资源占用： 低，单连接占用少
  • 适用： 高并发推送场景

WebSocket 性能特点

  • 连接数： 受限于服务器资源（通常几千）
  • 延迟： 极低，适合实时交互
  • 资源占用： 较高（需心跳保活）
  • 适用： 低延迟、双向通信场景

总结

选择 SSE 的场景

  1. ✅ 单向数据推送（AI 对话、监控、通知）
  2. ✅ 需要简单可靠的实现
  3. ✅ 需要自动重连机制
  4. ✅ 需要穿透各种代理和防火墙
  5. ✅ 数据量大的高频推送

选择 WebSocket 的场景

  1. ✅ 需要双向实时通信
  2. ✅ 需要发送二进制数据
  3. ✅ 需要极低延迟
  4. ✅ 需要复杂的交互逻辑
  5. ✅ 需要全双工通信

最佳实践建议

  1. 单一职责原则：根据功能选择合适技术
  2. 混合使用：同一应用可同时使用两种技术
  3. 渐进增强：从简单场景开始，逐步优化
  4. 错误处理：完善的异常处理和重连机制
  5. 性能监控：实时监控连接状态和数据流

一、传统账号密码登录

详细步骤：

  1. 前端发起登录请求 → POST /wxlogin
  2. 后端接收并校验参数 → 验证nickName、avatar、code
  3. 调用微信API获取openid → 通过code换取openid
  4. 数据库查询/创建用户 → 以openid为主键
  5. 生成JWT Token返回 → 有效期100天
  6. 前端保存Token → 用于后续API调用

2. 认证流程

  • 需要认证的接口使用 authority 中间件
  • 通过Basic Auth从请求头获取token
  • 验证JWT token有效性（包括过期检查）
  • 将用户信息注入 ctx.auth.uid
