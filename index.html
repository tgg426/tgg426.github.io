一、冒泡排序 Bubble Sort

算法原理

  • 交换排序，核心是“冒泡”：相邻元素比较并交换，让较大（或较小）元素逐步移动到末尾（或开头）。
  • 外层循环逐步缩小未排序区间；内层循环两两比较并交换。
  • 复杂度：平均/最坏时间 O(n^2)，空间 O(1) 原地排序，稳定。

方法一：简单冒泡

方法二：双向冒泡（鸡尾酒排序）

正向冒泡找到最大值移动到右端，反向冒泡找到最小值移动到左端，可在部分有序时减少遍历。

二、选择排序 Selection Sort

算法原理

  • 在未排序区间中选择最小元素，与未排序区间的第一个元素交换，扩充已排序区间。
  • 外层循环确定未排序区间起点，内层循环在未排序区间中寻找最小值索引。

复杂度与特性

  • 时间复杂度：平均/最坏 O(n^2)
  • 空间复杂度：O(1) 原地排序
  • 稳定性：不稳定（相同元素可能交换导致相对次序改变）

三、插入排序 Insertion Sort

算法原理

  • 构建有序序列；对未排序数据，在已排序区间中从后向前扫描，找到位置后插入。
  • 原地排序：空间复杂度 O(1)。
  • 可用二分查找优化插入位置的寻找，但元素移动次数不变，总体时间复杂度仍为 O(n^2)。

方法一：直接插入排序

方法二：二分插入排序（折半插入）

复杂度与特性

  • 时间复杂度：平均/最坏 O(n^2)
  • 空间复杂度：O(1)
  • 稳定性：稳定

四、希尔排序 Shell Sort

算法原理

  • 将序列按步长 gap 分成若干子序列，分别进行直接插入排序；不断缩小 gap，直到 gap 为 1。
  • gap 大时子序列短、排序快；gap 变小后整体已近乎有序，插入排序高效收敛。
  • 不稳定排序；时间复杂度取决于 gap 序列，常见实现约为 O(n log n)；空间 O(1)。

const shellSort = function (arr) {
let len = arr.length;
let temp = null;
let gap = Math.floor(len / 2);

while (gap > 0) {
for (let i = gap; i < len; i++) {
temp = arr[i]; // 先拿到索引为 gap 的元素
let j = i - gap; // 再拿 temp 前面间隔 gap 的元素
// 交换
while (j >= 0 && arr[j] > temp) {
arr[j + gap] = arr[j];
j -= gap;
}
arr[j + gap] = temp;
}
gap = Math.floor(gap / 2);
}

return arr;
};

LLM 流式回复：动画与微交互手册

引言

在大模型对话类应用中，良好的流式反馈不仅提升“响应速度”的体感，还能显著降低阅读负担与界面抖动。本文整理了常用的动画/微交互清单，并提供贴合 Vue 3 的示例代码。

🧭 动画与微交互清单

  • 基础反馈
    • 脉冲/波纹加载点: 在消息气泡内显示呼吸式圆点，表示正在生成。
  • 打字光标闪烁: 在末尾显示“|”光标，随内容增长持续闪烁。
  • 文本出现方式
    • 逐字/逐词显现: token 到达即追加，配合轻微淡入（opacity/translateY）。
  • 行级渐显: 按换行分段淡入，降低频繁重排带来的抖动。
  • 语句级过渡: 句号/逗号后块级 reveal，阅读节奏更稳。
  • Markdown 与代码块
    • 代码块整体淡入: 块级到齐后统一显现，减少半渲染闪烁。
    • 语法高亮延迟应用: 流式完成后再高亮，或节流批量高亮。
  • 逐行高亮闪现: 新增行短暂背景高亮再退场，提示位置变化。
  • 滚动与定位
    • 首帧平滑滚动: 开始回复时滚到底部一次。
    • 智能跟随滚动: 仅当用户在底部时自动跟随；离开底部则显示“回到底部”浮标。
  • 新内容定位提示: 当用户回到底部时，对最新 token 进行短暂高亮。
  • 来源/检索信息（RAG）
    • 可折叠来源面板: 展开/收起过渡（height auto → max-height）。
  • 命中文档闪现: 新增来源条目淡入并带轻微缩放。

  • 文本内引用 hover 高亮: 悬停引用标签，同步高亮对应来源条目。

  • 文件与图片回复

    • 缩略图占位骨架: 图片未就绪时显示灰色骨架与闪动光泽。

    • 图片加载淡入: onload 后从 0→1 的 opacity 过渡。

  • 消息气泡与布局
    • 气泡增长过渡: 内容增加时，使用 height/transform 过渡减缓突变。
    • 时间戳/操作区淡入: hover 或完成后显示复制、点赞等操作按钮。
  • 交互微动效
    • 复制成功反馈: 复制按钮触发勾号替换并回弹。
    • 停止生成按钮: 按下后显示停表/旋转到停止的过渡。
  • 状态切换
    • 输入禁用到恢复: 生成中禁用输入，完成时按钮/输入框淡入启用。
  • 错误显现: 错误条目从顶部下落或抖动，文案/重试按钮淡入。
  • 可访问性与性能建议
    • 减少布局抖动: 使用 will-change, transform, opacity，避免频繁 DOM 重排。
    • 节流渲染: 合并 token 为批量更新（如 16ms/帧）。
  • A11y: 为动态区域加 aria-live="polite"；动画时长控制在 150–300ms。

结语

选择合适的动画强度与节奏，优先保障可读性与性能；针对不同内容类型（段落、代码、图片、来源），组合使用合适的过渡策略，既“快”又“稳”。

  • 特征: 最常见的结构化响应。
  • 处理: 小程序 wx.request 会在 success.res.data 给出已解析对象（若服务端正确设置 Content-Type）。

2) 纯文本（text/plain）

  • 特征: 文本内容，无结构。
  • 处理: 直接作为字符串使用；如为 Markdown，交给渲染器（如 towxml）。
  • 示例（Markdown 渲染）:

3) SSE 流式数据（text/event-stream）

  • 特征: 单向、按行事件（形如 data: {...}\n\n），适合 AI 对话流、监控推送。
  • 处理: 小程序用 enableChunked: true + onChunkReceived；累积到 buffer，按 \n 切割，解析以 data: 开头的 JSON，忽略 [DONE]。

  • 特征: 双向、低延迟，可文本/二进制，适合实时聊天、协同编辑、音视频控制。
  • 处理: 管理连接、心跳、重连；消息按协议字段区分类型。

5) 二进制（ArrayBuffer/Blob、图片/音频）

  • 特征: 文件、媒体流、模型参数等。
  • 处理:
    下载：wx.downloadFile 或 wx.request 的 responseType: 'arraybuffer'（H5 用 fetch Blob）。
    显示图片：拿到 URL 或临时路径直接 <image src="..."/>。
  • 示例（下载图片并预览）:

6) NDJSON（换行分隔 JSON）

  • 特征: 每行一个 JSON，常用于日志/流式批处理。
  • 处理: 与 SSE 类似，按行切割后 JSON.parse 每行；注意半包合并。
  • 示例:

  • 处理: 轻量可 split('\n').map(r=>r.split(','))；复杂用库（H5 可用 PapaParse，小程序需自带解析）。

8) 表单与文件上传（multipart/form-data, application/x-www-form-urlencoded）

  • 特征: 表单字段与文件混合。
  • 处理: 用 wx.uploadFile 处理文件；普通表单用 wx.request 传对象（小程序会序列化）。

9) Base64 数据（data URI / 纯 base64）

  • 特征: 图片/音频内嵌编码。

建议

  • 与后端约定响应头：Content-Type 准确决定解析方式。
  • 流式数据统一解析器：SSE/NDJSON 共用“行缓冲 + 解析”的工具函数。
  • 健壮性：半包合并、异常 JSON try/catch、自动重连（SSE/WS）。
  • 类型与协议：为 WebSocket 消息定义 type 字段，便于路由处理。
  • 性能：批量渲染/合并 setState，减少频繁重绘（如 AI 流式逐字追加时）。
  • 安全：富文本/Markdown 渲染需防范 XSS（受控渲染器、白名单）。

二、Web端环境

1) JSON（application/json）

  • 特征: 结构化对象，最常见。
  • 处理: fetch().then(r=>r.json())；注意错误码不抛异常，需自判。

2) 纯文本（text/plain）

  • 特征: 文本响应。
  • 处理: response.text()；若为 Markdown，交给渲染器（marked、markdown-it）。

3) SSE 流式数据（text/event-stream）

  • 特征: 服务端→客户端单向推送，自动重连。
  • 处理: 使用 EventSource；从 event.data 取字符串，再按需 JSON.parse。

4) Fetch 流式读取（ReadableStream / NDJSON）

  • 特征: 分块返回，行分隔 JSON、日志等。
  • 处理: 读取 response.body 的 ReadableStream，使用 TextDecoder 解码，做“行缓冲”。

5) WebSocket（ws/wss）

  • 特征: 全双工、低延迟，文本/二进制皆可。
  • 处理: 管理心跳、重连；消息按 type 路由。

6) 二进制（Blob/ArrayBuffer，图片/音频/文件）

  • 特征: 文件下载、媒体、模型参数。
  • 处理: response.blob() 或 response.arrayBuffer()；通过 URL.createObjectURL 预览。

7) CSV（text/csv）

  • 特征: 表格数据。
  • 处理: 简单可手写解析；复杂用库（Papa Parse）。

8) 表单与文件上传（multipart/form-data, x-www-form-urlencoded）

  • 特征: 字段与文件混合或表单编码。
  • 处理: FormData 配合 fetch；无需手动设置 Content-Type（浏览器自动）。

9) Base64 / Data URL

  • 特征: 内嵌编码的媒体数据。
  • 处理: 直接赋给 src；或转 Blob 以减小内存峰值。

10) Markdown/富文本（XSS 安全）

  • 特征: 富文本、表格、代码块。
  • 处理: 使用可信渲染器，启用 XSS 过滤（DOMPurify）。

建议

  • Content-Type 与状态码：先判 response.ok，再按类型解析（json/text/blob）。
  • 流式渲染节流：高频增量（AI 字符流）批量合并（requestAnimationFrame/计时器）。
  • 重连策略：SSE 自动；WebSocket 指数回退并带抖动，心跳保活。
  • 内存管理：用完的 Blob 调用 URL.revokeObjectURL；大型数组分片处理。

引言

在实时应用开发中，选择合适的通信协议至关重要。WebSocket 和 SSE（Server-Sent Events）是两种常用的流式数据传输技术，各自有不同的应用场景和优势。本文将深入分析这两种技术，并根据不同业务场景提供选型建议。

核心技术对比

SSE (Server-Sent Events)

核心特征：

  • 📡 单向通信：服务端 → 客户端
  • 🔗 基于 HTTP 长连接
  • 🔄 自动重连机制
  • 📝 仅支持文本数据
  • 🚀 实现简单

WebSocket

核心特征：

  • 📱 双向通信：服务端 ⇄ 客户端
  • 🔌 独立协议（ws://, wss://）
  • ⚙️ 需手动实现重连
  • 📦 支持文本和二进制数据
  • 🎯 低延迟、高性能

IoT 设备控制 WebSocket 双向控制，实时响应

性能对比

SSE 性能特点

  • 连接数： 可支持数万并发连接
  • 延迟： 略高于 WebSocket（HTTP 开销）
  • 资源占用： 低，单连接占用少
  • 适用： 高并发推送场景

WebSocket 性能特点

  • 连接数： 受限于服务器资源（通常几千）
  • 延迟： 极低，适合实时交互
  • 资源占用： 较高（需心跳保活）
  • 适用： 低延迟、双向通信场景

总结

选择 SSE 的场景

  1. ✅ 单向数据推送（AI 对话、监控、通知）
  2. ✅ 需要简单可靠的实现
  3. ✅ 需要自动重连机制
  4. ✅ 需要穿透各种代理和防火墙
  5. ✅ 数据量大的高频推送

选择 WebSocket 的场景

  1. ✅ 需要双向实时通信
  2. ✅ 需要发送二进制数据
  3. ✅ 需要极低延迟
  4. ✅ 需要复杂的交互逻辑
  5. ✅ 需要全双工通信

最佳实践建议

  1. 单一职责原则：根据功能选择合适技术
  2. 混合使用：同一应用可同时使用两种技术
  3. 渐进增强：从简单场景开始，逐步优化
  4. 错误处理：完善的异常处理和重连机制
  5. 性能监控：实时监控连接状态和数据流
